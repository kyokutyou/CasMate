# PC・Android通信統合の検証

2026-10-03。対象仕様は [PC・スマホ間の通信](../features/smartphone-transport.md)。比較元は `3db6728ff397c2ba2908c64b4c05d1f3419b7e9e`。本書は測定記録であり、正式仕様を追加しない。

## 経路の棚卸し

| PC・スマホ間の用途 | 改修後 |
| --- | --- |
| コメント履歴・差分・表示設定 | 読取専用 `/mobile/ws`、版2。Androidネイティブが購読し、WebViewには表示データだけを渡す |
| 読み上げ・試聴のM4Aと再生応答 | 同じ読取接続のバイナリ。端末は再生中1件と先読み1件をメモリに保持 |
| OBSの状態・開始・終了・確認取消 | 登録ポートの認証付き `/smartphone/ws`、版1 |
| 外配信の端末状態・PC受信確認 | 同じ認証付き接続。状態は変化時、受信証拠は最大250ms間隔 |
| 映像・配信マイク | 前回改修したネイティブSRTを維持。PC受信後、ループバックUDPでOBSへ渡す |
| 共通QRからの端末登録 | HTTPを維持。応答版8で共通制御URLを渡す |
| コメント画面・静的ファイル・bootstrapメタデータ | HTTPを維持。履歴・音声・制御の取得には使用しない |

旧OBS専用3002待受と、音声取得・OBS操作・外配信状態・受信確認のHTTP経路は廃止。コードの呼出元も確認し、AndroidのHTTP要求生成は登録処理だけに集約されている。PC内の管理API、OBS WebSocket、音声合成サービス等はPC・スマホ間通信とは別の経路であり、今回の統合対象に含めない。

## 実機と測定方法

Windows PCとPixel 10a（Android17 / API37）を同一LANで接続。旧版の保存済みPCビルド・APKと新しいビルドを順番に使用する。端末登録は試験前の暗号化ファイルまたは登録オブジェクトを保持し、試験後に復元する。

[測定サーバー](../../tools/measure-smartphone-transport.mjs)と[Android実機テスト](../../android/app/src/androidTest/java/jp/casmate/app/obs/SmartphoneTransportDeviceTest.kt)を使用。履歴1,000件、コメント30件、OBS状態変化30回、準備済みAAC-LC/M4A（24kHz・mono・32kbps・250ms・2,078bytes）30件、読取サーバー切断・600ms後の再開30回、画面ロック中の音声3件。音声合成は行わない。OBS状態の速度測定は合成状態であり、実際のOBS操作とは別の試験とする。

PCでの送信開始、または音声準備完了から、端末側の描画・状態反映・Media3の `isPlaying` を観測してPCへ戻す応答までをPCの同一単調時計で測る。端末間の時計差は使わない。戻り通信と観測待ちを含むため、純粋な一方向遅延より大きい。再接続値には試験で与える600msの停止を含む。転送量は対象2ポートのTCP socket bytes、測定用HTTPポートは除外。暗号化・IP等の下位層オーバーヘッドは含めない。

## 比較結果

ビルド・全体テストを終了してから旧版・新版を順番に測定した。最終実機テストは旧版163.482秒、新版108.091秒でどちらも成功。[各標本と集計値](./smartphone-transport-2026-10-03.measurements.json)を保存している。

| 測定対象（各30標本） | 旧方式 p95 | 新方式 p95 | 目標 |
| --- | ---: | ---: | ---: |
| コメント描画 | 34.8ms | 46.2ms | 500ms以下 |
| OBS状態反映 | 2,046.2ms | 24.7ms | 500ms以下 |
| 音声準備完了→実再生開始 | 222.9ms | 186.2ms | 750ms以下 |
| 読取接続の復帰 | 1,578.6ms | 1,691.0ms | 5,000ms以下 |

コメントと再接続の測定値は少し増えたが目標内。OBSのポーリング待ちと音声のHTTP取得を削減した効果を確認できた。このLAN・端末・標本数の結果であり、他の端末やインターネット回線で同じ値を保証するものではない。

| 同じ件数の処理 | 旧方式の送受信量 | 新方式の送受信量 | HTTP要求（旧→新） |
| --- | ---: | ---: | ---: |
| 待機30秒 | 12,808 bytes | 6,235 bytes | 14→0 |
| 音声30件 | 189,971 bytes | 79,365 bytes | 66→0 |
| 再接続30回と履歴再同期 | 27,515,031 bytes | 8,793,628 bytes | 53→0 |

待機は約51%、音声は約58%、再同期は約68%の通信量削減。再接続時のWebSocket Upgradeは60回から30回に減った。音声・再同期の処理時間は旧新版で異なり、表にはその期間のOBSポーリング／heartbeatも含む。初回の静的ファイル取得量はキャッシュ条件が異なるため上表には含めない。

旧新版とも画面消灯とKeyguardロックを確認した後、3件の音声の実再生を確認。通知の「停止」でサービス停止、開始希望の保存値がfalseになることも確認した。試行中に端末のロック猶予時間に対して5秒の待機が短くタイムアウトしたため、ロック完了待機を20秒へ延ばして再実行した。端末のロック設定そのものは変更していない。

## 実際のOBS操作

インストール済みOBS32.2.2を作業用フォルダーへコピーし、[公式のportable mode](https://obsproject.com/kb/portable-mode)で隔離。専用プロファイル、認証付きWebSocket4465、合成色画面、`127.0.0.1` のRTMP受信だけを使用した。開始前に専用プロファイル名・出力先・キーを検証し、本番OBS設定は変更していない。

新しいAndroid接続から準備→確認→実状態反映を開始・終了それぞれ1回実行し成功。準備だけでは状態が変化しないこと、実際の開始要求1回・終了要求1回、受信FFmpegの映像7フレームを確認。操作後は停止し、隔離プロセスを終了した。

## 登録・映像・ブラウザー

Pixel 10aの既存登録から共通QRを使った応答版8への登録を2回行い、端末IDが維持され、二重登録にならないことを確認した。登録済みの実際のPCでSRT送受信、状態報告、受信済み映像IDの増加、明示停止が成功した。

さらに制御用WebSocketだけを再接続し、制御接続IDが変わった後に状態報告と受信済み映像IDの増加が復帰することを確認。SRT送信の世代は変わらず、送信状態を維持した。映像・音声の保存やOBSからの外部配信は行っていない。

PCのChromium系ブラウザー（Codex内蔵ブラウザー）で通常の `/comments` を開き、1,000件の履歴表示、音声開始・停止、M4Aの再生開始応答1件・終了応答1件、エラー表示なしを確認した。これはAndroidの埋込み画面とは別のブラウザー経路を使用する。Chrome・Edgeを個別に起動した検証は未実施。

## 環境上の制約

TailscaleはPCのBackendStateがStopped、オンライン端末0件のため、Tailscale経由の実測は未実施。ネットワーク別の認証・切替は自動テストで検証した。物理的な端末再起動と長時間のDoze待機は実施していない。再起動後の自動再開禁止はBOOT_COUNTを変更する回帰テストで確認した。
