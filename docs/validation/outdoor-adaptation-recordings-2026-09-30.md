# 外配信・提供録画の追加検証（2026-09-30）

## 結論

H.265の自動ビットレート低下、静止、復帰試行、動画再開と段階的な増加を、スマホ画面とOBS録画の両方で確認した。永久に静止したままになる現象は今回の録画にはない。一方、最初の大きな低下では静止と試行を約34秒繰り返し、OBSには約10秒の連続静止もある。「復帰する」ことは確認できたが、常に短時間で復帰する・全体に問題がないという判定にはしない。

**今回の録画では音声継続は不成立。原因は画面録画とのマイク競合だった。** 録画開始時にAndroidがきゃすメイトのマイクを無音化した記録を、接続端末から確認した。OBS録画は約2.20秒以降、最後まで無音。利用者も「音声が確認できたのはスマホ録画で、SRT映像には音声が載っていない」と確認した。

これは利用者が任意に提供した追加録画の検証である。[先行するH.264の短い実機確認](./outdoor-adaptation-device-2026-09-30.md)とは条件・結果を分ける。先行確認をH.265＋画面録画中の音声継続成功へ拡張しない。正式な受け入れ条件は[外配信仕様](../features/outdoor-streaming.md#自動制御の再設計版の受け入れ条件)を参照する。

| 端末での追加確認 | 起動済みアプリは0.4.0、送信停止中。Androidの録音状態履歴を読み取り、きゃすメイトと画面録画に関係する時刻・状態だけを記録 |

録画ファイルのH.264は保存時の形式であり、スマホからOBSへの送信形式H.265とは異なる。録画だけで送信エンコーダー名・全設定・回線容量を断定しない。

元ファイルは変更していない。全体を順次デコードし、OBS全7401フレームの画像差分、毎秒の焼き込み時刻、スマホの約0.5秒ごとの状態・数値表示を確認した。OCRを調査補助に使い、主要場面は抽出画像で確認した。シークによる抽出で文字の欠けが出た画像は根拠にせず、順次デコードの画像を採用した。音声は全区間をPCMにデコードして解析しており、エージェントによる直接の聴取成功とは記録しない。

2本の録画は開始時刻が異なる。以下はそれぞれのファイル先頭からの再生時刻で、区間は約0.5～1秒単位の概数。録画位置の差をそのままSRT遅延・OBS遅延とは扱わない。

長い保持区間の後も焼き込み時刻が現在側へ進み、古い動画を長く順番に再生し続ける様子は主要な復帰場面では見られない。これは精密な遅延測定ではない。

スマホにはRTTが数秒に増えた場面や「送信待ちの混雑候補」がある。画面上の送信待ち件数が0でも、内部の処理中・未ACK・最古待ち等がすべて0とは限らない。この回の数値診断JSONは得られていないため、各試行失敗の直接原因や、回線容量に対して静止判断が過敏かどうかは未確定。映像目標の低下と増加は確認できるが、API受付表示だけで全時点の実出力追従を合格にしない。

## 音声停止の根拠

OBSファイル内の音声トラックを48kHz・左右2チャンネルのPCMへ展開すると、浮動小数点デコーダーで最後の非ゼロ標本は再生位置2.1973125秒。その後は両チャンネルともゼロだった。別の固定小数点AACデコーダーでも3秒以降は一定の微小DC値のみで、時間変化・音声信号がないことを再確認した。

スマホ画面は開始時の「マイク：有効」から開始直後に「マイク：入力未確認」へ変わり、その後も維持する。映像の最初の大きな低下より前に音声が止まっている。

Androidの録音状態履歴には、次の順序が残っていた。時刻は端末の現地時刻。UID・録音セッションID等は省いた。

| 時刻 | Androidの記録 |
| --- | --- |
| 22:22:27.462 | きゃすメイトの`MIC`は`not silenced` |
| 22:24:45.092 | 画面録画側が`REMOTE_SUBMIX`を使用 |
| 22:24:45.109 | きゃすメイトの`MIC`が`silenced`へ変化 |
| 22:24:45.126 | 画面録画側が`VOICE_COMMUNICATION`を使用、`not silenced` |
| 22:28:50.669 | きゃすメイトの`MIC`に対するOSの無音化が解除 |
| 22:28:50.686 | 画面録画側の`VOICE_COMMUNICATION`が停止 |

Androidは同時の音声入力を優先順位で調整し、優先されない入力へ無音を返す。`VOICE_COMMUNICATION`と通常のマイク入力の競合は[Android公式の音声入力共有ルール](https://developer.android.com/media/platform/sharing-audio-input)に対応する。今回は一般論による推測だけでなく、同時刻のOS記録・スマホ表示・OBS録音を合わせて原因を特定した。

きゃすメイトの[SelectedMicrophone](../../android/app/src/main/java/jp/casmate/app/outdoor/SelectedMicrophone.kt)はOSの`isClientSilenced`を入力喪失として検出する。現行の[入力喪失時の仕様](../features/outdoor-streaming.md#android操作)どおり、入力喪失後は利用者が入力を再選択・再開するまで無音を維持する。OS側の競合が解消しただけでは、自動でマイク音声を復帰させない。

## 検証後の状態と次の確認方法

- 製品コード・品質設定・登録・OBS設定は変更していない。端末の送信は停止のまま、確認のため閉じた通信詳細は元へ戻した。
- 追加の映像・音声録画は行っていない。PCのOBS WebSocketには接続できなかったため、今回の端末確認はOS記録と停止状態の読み取りまで。音声復旧の実送信再試験は実施していない。
- 音声を含む確認では、スマホの画面録画によるマイク収録をオフにするか、画面録画を止める。送信中に入力喪失が残っていれば、外配信設定の配信マイクにある「入力再開」、または同じマイクの再選択を使う。これは現行仕様・実装で確認した復旧操作である。
- 映像復帰の速さを改善する判断には、この回と同じ条件の数値診断で、混雑判定・試行中止・未ACK・実生成量を照合する必要がある。今回の録画だけで閾値を変更しない。

今回の変更は検証記録のみ。先行する自動テスト・ビルド結果を再実施したとは記録しない。
