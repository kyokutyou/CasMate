# 開発の運用手順

本書は[AGENTS.md](../AGENTS.md)から参照する開発手順を所有する。変更に関係する節を読み、製品の挙動は[SPEC.md](../SPEC.md)と機能別仕様で確認する。

## 文書の役割

- SPEC.mdは概要・目的、開発対象バージョン、実装対象機能と短い説明、機能別仕様へのリンク、OUT_OF_SCOPE.mdとFUTURE_IDEAS.mdへのリンクを持つ入口とする。
- docs/features/は機能の具体的な挙動・条件・例外・他機能との関係を所有する。共通の画面規則は管理画面仕様、各編集画面の詳細は機能仕様、保存・API等の共通契約はローカルアプリケーション仕様が所有する。
- CONTEXT.mdは正式用語、docs/adr/は重要な設計判断を所有する。研究・比較見本・過去の検証記録は正式仕様の代わりにしない。
- 機能仕様の「調査入口」は主な実装・代表テスト・関連仕様への案内であり、仕様や影響範囲の全件一覧ではない。変更前に実際の参照元と関連テストを検索する。入口のリンク先を移動・削除した作業で案内も更新する。

## 検証手順

### 作業中と完了時

1. 変更種別と影響範囲を判断する。直前の検証後の差分・依存関係・実行環境も確認する。
2. 変更箇所と参照元から、先に通す関連テストのファイルと実行コマンドを特定する。共通部品・共有処理だけでなく、テスト用ヘルパー・フィクスチャー・起動処理を変更する場合も、その利用先すべてを調べる。影響する機能・実行分岐・描画エンジンを含め、範囲が不明なら調査と対象を広げる。
3. 実装中は失敗ケースを絞って再現・修正し、必要な回帰テストを追加・更新する。既存テストで十分な場合は実装をなぞるだけの重複テストを増やさない。
4. 実装とレビュー修正をまとめた後、手順2で特定した関連テスト群をすべて成功させる。個別ケースの絞り込みを外し、共通処理の利用先を含む対象テストファイル全体を実行する。成功した一部のケースだけで完了とせず、対象と全件成功を短く確認してから最終検証へ進む。
5. 関連テストがすべて成功した状態で `pnpm lint`、`pnpm typecheck`、最後の全体テストとして `pnpm test`、その成功後に `pnpm build` を実行する。全体テストを既知の不具合の修正途中で繰り返さない。負荷による失敗を混ぜないよう、全体テストは関連テスト・lint・型チェック・ビルドと並行して実行しない。変更種別による実施範囲は次表に従う。
6. 成功後にコード・設定・依存関係・環境が変われば影響する検証を再実行する。まず関連テストの範囲を見直し、すべて成功させてから必要な最終検証へ戻る。共有処理・API・保存・依存関係・検証設定の変更や影響不明では、関連テスト成功後に全体検証も再実行する。必要な再検証に回数の上限は設けない。
7. 対象仕様が求めるUI・Electron・Android・実サービスの確認を行う。管理画面の対象・幅・環境は[画面確認の範囲](features/management-screen.md#画面確認の範囲)で判断する。仕様が認める描画の自動検証以外で実機確認を代替せず、できなければ未検証の範囲を報告する。

関連テスト群が全体テストと同じ範囲になる場合は、局所的な再現・修正とlint・型チェックを済ませてから全体を実行し、その全件成功を関連テストと最終全体テストの両方の確認とする。同じ差分・同じ条件で全体テストを重複実行しない。

### 変更種別

| 種別 | 最終確認 |
| --- | --- |
| 製品コード、CSS、テストコード、依存・ビルド・検証設定 | lint、型チェック、全体テスト、ビルド。対象仕様に応じた画面・実機確認 |
| 純粋な文書の移動・リンク・表記整理 | 差分、リンク先・アンカー、所有範囲、移動前後の条件・例外の保存を確認。製品コードが不変なら全ビルドを要求しない |
| 正式仕様の意味変更 | 実装・既存テストとの整合を確認。コードも変える場合は全体検証。文書だけで完了とする理由と未実装の有無を明示 |
| AGENTS.md等の運用変更 | 旧ルールとの対応、参照先、作業例で判断が一意になるか確認。スクリプトも変える場合はコード変更として検証 |

拡張子だけで分類しない。生成・配布・テスト・アプリ実行が読む文書やテンプレートは利用側も検証する。仕様変更後に実装が追いついていなければ「仕様更新済み・実装未完了」と区別し、実装を含む依頼の完了にはしない。機能仕様の実機確認・受け入れ条件は上表で免除しない。

### 失敗と再実行

- 失敗したコマンド、対象差分、要点を記録し、原因に対応する修正・条件変更後に再実行する。同条件で成功するまで繰り返さない。失敗・未実施を成功扱いしない。
- 全体テストで失敗した場合も、先に失敗箇所を絞った再現・修正と、影響する関連テスト群すべての成功確認へ戻る。1件を直した直後に全体テストを再開せず、共通処理を変えた場合は他の利用先も含めて確認する。
- lint・テスト対象を変える場合は、分離前後の集合を比較し、製品ソース・テスト、ルート設定、開発ツール、新規ディレクトリの検査に欠落がないことを確認する。一部だけの実行を全体成功と同一視せず、通すためだけの除外や不正パスの無断削除をしない。
- `pnpm lint`は[実行スクリプト](../tools/lint.mjs)でGitの追跡済みファイルと除外対象外の未追跡ファイルを列挙し、既存のESLint設定を適用する。製品ソース・テスト、ルート設定、開発ツール、新規ディレクトリを対象とし、`prototypes/`と[明示した見本専用テスト](../tools/prototype-tests.json)だけを分離する。Git作業ツリーが必要で、Git除外済みの未追跡生成物・一時ファイルは対象外。無効な引数、列挙失敗、検査対象ゼロを成功扱いしない。
- `pnpm test`は製品の全体テストを実行する。比較見本を変更・再利用する場合は、見本ソースと見本専用テストの `pnpm lint:prototypes`、見本専用の `pnpm test:prototypes`も実行する。比較資料は保持し、通常の製品検証へ常時混ぜない。
- `pnpm test`は[実行スクリプト](../tools/test.mjs)で通常テストを4並列、その全件成功後に描画テストを2並列で実行する。Vitestが検出した対象を毎回分類し、実行直前にも各段階の対象を照合する。欠落・重複・ゼロ件は成功扱いしない。描画は共通のElectron起動ヘルパーをimportするテストと、`// @casmate-rendering`を付けたテストとする。通常ブラウザだけを起動するテストにもこの印を付ける。新規テストを固定リストへの追記漏れで除外しない。
- ファイル名・`-t`・`--testTimeout`等の指定は引き継ぐ。`--maxWorkers`を明示した場合は両段階へ適用する。レポーター・レポート出力（`--outputFile`）・カバレッジの指定、または名前付きプロジェクトの構成では、レポートの上書きや同一ファイルの別プロジェクト実行を失わないよう全対象を1回のVitest実行にまとめる（並列数の明示がなければ2）。監視実行は従来どおり`pnpm test:watch`を使う。通常の全体成功は両段階の全件成功を指し、片方の成功だけで完了としない。
- 描画後の固定待機を削減する場合も、判定・操作・画面条件・撮影内容は維持する。OBSデザイン検証は2フレームの描画と有限アニメーション、保存・取得の結果を待ち、未完了は期限付きで失敗にする。製品の500msの自動保存と、499ms／500msの境界を確認するテストは短縮しない。
- テストの並列数は再現条件と所要時間を確認して選ぶ。並列数を下げた成功だけで原因を確定しない。
- Electronの描画テストは[共通起動処理](../tests/helpers/electron-fixture.ts)を使い、子プロセスの作業ディレクトリをテスト専用の一時フォルダーへ固定する。手動のElectron検証でも起動前に絶対パスの一時フォルダーを `cwd` に指定し、スクリプト・HTML・出力先も絶対パスで渡す。CodexのWindowsサンドボックス内ではWindowsのスペルチェック初期化が文字化け名の `Microsoft/Spelling/neutral` を相対パスで作る現象を確認しており、Electronの `userData` 指定やスペルチェック無効化だけでは防げない。2026-10-07の比較では、同じAPIを通常のWindows権限で実行すると初期化が成功し、文字化けフォルダーも生成されなかった。一時フォルダーへの隔離はプロジェクト直下への生成を防ぐ対策であり、Windows側の生成不具合を直すものではない。起動・描画失敗を成功扱いせず、設定・権限の確認と再実行は通常の手順に従う。
- 検証結果は対象差分、コマンド、成否、未確認点・制約を完了報告へ短く記載する。毎回の詳細な検証記録ファイルは作らない。実機の測定値や複雑な再現条件など、保存して後から参照する必要がある場合だけ別ファイルに残す。機能仕様が求める記録条件と過去の記録は保持する。ログ全文は必要時に参照する。配布物の生成条件はAGENTS.mdに従う。

## Windows配布物の生成と証明書エラー

2026-10-24、このPCで electron-builder 26.15.3 / Electron 43.4.1 のパッケージ時に `unable to verify the first certificate` が発生した。`NODE_USE_SYSTEM_CA=1` を設定した子プロセスでは、インストーラー・展開版の生成がともに成功した。証明書チェーンの具体的な不足箇所は未特定。以下はこの環境での確認済み手順とする。

### 最初から適用する設定

PowerShellでプロジェクトを開き、配布コマンドと同じセッションで設定する。

```powershell
$env:NODE_USE_SYSTEM_CA = '1'
```

Windowsの信頼済み証明書をNode.jsでも利用する。証明書検証は維持する。環境変数は現在のPowerShellとその子プロセスに適用され、マシン全体の永続設定は変更しない。Codexの別の exec_command 呼出しには引き継がれないため、**配布コマンドを実行する呼出しごとに、同じコマンド内で設定する**。設定せずに一度失敗させる手順にはしない。

### インストーラー

```powershell
$env:NODE_USE_SYSTEM_CA = '1'
pnpm package:win
```

アプリの再ビルド後、`release/CasMate-Setup-<version>.exe` を生成する。

### 展開版

ソース変更後にまだビルドしていない場合は、先に `pnpm build` を実行し、成功を確認する。現在のソースで既にビルド成功済みなら重複実行は不要。

```powershell
$env:NODE_USE_SYSTEM_CA = '1'
pnpm exec electron-builder --win dir
```

生成先は `release/win-unpacked/`。起動は同フォルダー内の `CasMate.exe`。配布時はEXE単体ではなく、フォルダー全体を渡す。ZIPにまとめた場合は、必要ファイルの欠落がないことを確認する。

### 証明書エラー後の再実行

- ログで、アプリのビルド失敗と electron-builder のパッケージ失敗を区別する。
- ビルド成功後、パッケージだけが失敗し、その後ソース・依存関係・ビルド設定が変わっていない場合は、証明書設定を付けて `pnpm exec electron-builder --win nsis`（インストーラー）または `pnpm exec electron-builder --win dir`（展開版）だけ再実行する。
- それでも証明書検証に失敗する場合は、Node.jsの実行バージョン、当該プロセスの環境変数、失敗した接続先、Windowsの信頼済み証明書・プロキシ環境を確認する。同条件で繰り返さない。
- `NODE_TLS_REJECT_UNAUTHORIZED=0` や `strict-ssl=false` による検証の無効化は使わない。
- 成功はコマンドの終了コード0と成果物の更新日時・サイズで確認する。古いEXEが残っているだけでは成功としない。今回のような画面修正は、梱包した `resources/app.asar` に変更が含まれることも確認する。インストール・実機動作確認の有無は別に報告する。

配布物を作る条件はAGENTS.mdに従い、全体テスト等の実施範囲は今回の利用者の指示と検証手順に従う。この手順の追加自体では配布・全体テストを実行しない。

## レビュー判断

全変更で要求との一致、影響範囲、例外・失敗時、検証結果を担当者が確認する。ファイル数や行数だけで低リスクと判断しない。

共有処理、設定移行、公開・認証、外部書込み、配信制御、複数機能にまたがる変更、仕様の曖昧さを解消した変更、運用ルールの変更では、編集工程を終えてから「仕様との一致」と「故障時・影響範囲」の2観点を分けて追加レビューする。UIでも状態管理・保存・非同期表示を変えれば該当する。

別担当の独立レビューを利用でき、利用が許可される場合は優先する。利用しない場合は担当者が2観点を別々に確認し、自己レビューであることと制約を記録する。重大な未解決指摘は解消するまで完了扱いにしない。

適用する指示・スキルが独立レビューや複数観点を必須とする場合は省略しない。必須レビューを避けるために手順を選び直さない。独立レビューの実施と自己レビューを混同しない。

減らすのは原文の無意味な再取得、大量の成功ログ、短間隔の状態確認、同じ観点の二重確認であり、不具合を見つけるレビューの品質ではない。

## 互換性を整理する手順

1. 対象契約の所有仕様とADRを更新する。アプリのビルド番号とは独立に、必要な契約だけ対応範囲を変更する。
2. compatibility-policy.jsonを変更し、pnpm compatibility:generateを実行する。対応する型・パーサーと招待→応答→通信版の組合せも更新する。
3. 対応終了した移行・認証・API・UIの利用箇所を検索して削除する。安全な旧保存の識別、原本退避、失敗時の復元は保持する。今回の版なし品質の導入入口も次回整理時に終了できる。
4. pnpm compatibility:checkで生成結果を確認し、契約単独の変更、現行保存の保全、旧形式拒否、退避失敗・中断・再起動を検証する。
5. 通常の全体検証と2観点のレビューを実施する。過去の検証記録は現行差分の検証済みとして扱わない。
