# 無コメント時の話題生成を継続料金なしで行う方式の調査

調査日: 2026-09-02  
対象: Windows 11向けローカルアプリ「きゃすメイト」で、一定時間コメントがないときに短い話題文を出す将来機能  
位置付け: この文書は調査メモであり、正式仕様ではない。実装するには機能別仕様書を作成し、`SPEC.md` の実装対象へ追加する必要がある。

## 結論

最も適しているのは、**自作の話題カードと型付きテンプレートを必須コアにし、ローカルの時刻・曜日・季節・配信者が選んだカテゴリで候補を絞る方式**である。

このコアは完全オフライン、API利用料なし、PC負荷がほぼなく、文章を出荷前に人間が確認できる。短い雑談コメントという用途では、自由生成の能力よりも、配信中に不自然・不適切な文を出さず、必ず短時間で応答できることの価値が高い。

無料の外部情報源とローカルLLMは、次の任意拡張にする。

1. 気象庁など利用条件を確認した情報源を、話題の「素材」として低頻度で取得する。
2. ローカルLLMは高性能PC向けに、承認済みの話題文を短く言い換える用途だけに使う。
3. 取得、モデル、生成、検査のどこかが失敗したら、即座に内蔵話題文へ戻る。

この段階的ハイブリッドなら、**継続料金なし・オフライン・低負荷という最低保証を崩さず**、希望する配信者だけが鮮度や文体の種類を増やせる。

## 前提と評価尺度

本書の「完全無料」は、既存PCと通常のインターネット契約を使う前提で、API従量課金、サブスクリプション、モデル利用料が発生しないことを指す。電気代、通信費、開発・保守工数までゼロという意味ではない。

実装難易度、PC負荷、自然さ、バリエーションは、公開仕様から直接決まる数値ではなく、きゃすメイトの現行構成に照らした工学的評価である。ローカルLLMの速度と品質は対象PCでの実測が必要である。

## 1. 自作の話題データから選ぶ

### 評価

- 完全無料運用: 可能
- 実装難易度: 低
- PC負荷: ほぼなし
- 自然さ: 人手で校正すれば高い
- バリエーション: 有限だが、カテゴリ分けと再使用制御で実用性を上げられる
- ネット依存: なし
- 障害耐性: 最も高い

すべてを単一の固定文として持つより、話題カードごとに複数の完成文を用意する方がよい。例えば「食事」「ゲーム」「睡眠」「休日」「季節」「趣味」の話題カードに、それぞれ3～5個の自然な言い回し、利用可能な時刻・季節、重複グループ、センシティブ区分を付ける。

文章を細かい単語へ分解し過ぎると、助詞や意味の組合せが崩れる。初期版では、短い完成文を人手で校正し、差し替えるスロットを型の合う少数の語へ限定するのが安全である。

プロジェクト自身が文章を新規執筆すれば、第三者の質問集や会話データの再利用条件を持ち込まない。外部データをコピーする場合は、そのデータ固有のライセンス確認が別途必要になる。

## 2. テンプレート・ルールによる手続き的生成

### 評価

- 完全無料運用: 可能
- 実装難易度: 低～中
- PC負荷: ほぼなし
- 自然さ: 中～高
- バリエーション: 中～高
- ネット依存: なし

外部通信なしで利用できる入力は次のとおりである。

- 現在時刻、曜日、月、季節
- コメントがない時間の長さ
- 直前に使った話題カテゴリと文型
- 配信者が設定した配信カテゴリ、趣味、避けたい話題
- 配信セッション中に使った話題ID

品質を保つには、スロットへ型を付ける。「食べ物」にだけ使える文型、「休日の行動」にだけ使える文型のように、意味の互換性をデータ上で制限する。同一文だけでなく、同一話題カテゴリと同一導入句にもクールダウンを設ける。

自然さと安全性のため、次を推奨する。

- 一回に出すのは短文一つだけにする。
- 直近20～50件の使用IDを配信セッション中だけ保持する。
- 無コメント状態が続いても連投せず、次回までの間隔へ揺らぎと上限を設ける。
- 医療、政治、災害、金銭、個人属性などを既定話題から除外する。
- URL、禁止語、長さ、同文、類似文を投稿前に検査する。
- 利用者がプレビューし、カテゴリ単位で無効化できるようにする。

## 3. Markov連鎖、n-gram、既存コメントの組み替え

### 評価

- 完全無料運用: 自作または適法に利用できるコーパスなら可能
- 実装難易度: 中
- PC負荷: 低
- 自然さ: 低～中
- バリエーション: 高
- ネット依存: なし

短い日本語コメントだけでは文法が崩れやすく、元コメントの一部をそのまま再現する可能性もある。視聴者コメントを材料にすると、個人情報、攻撃的表現、内輪話を別の文脈で再出力する危険がある。

きゃすメイトは現行仕様でコメント本文を永続化せず、不要な外部送信もしない方針である。[コメント取得仕様](../features/comment-acquisition.md) と [ローカルアプリケーション仕様](../features/local-application.md) を参照。この方針を維持して配信セッション中だけ学習しても、品質と安全性はテンプレート方式に劣る。

今回の用途では、主方式には勧めない。使う場合も、承認済みの語尾候補の重み付けなど、元コメント本文を再構成しない狭い用途に限定する。

## 4. ローカルLLM

### 推論エンジン

`llama.cpp` はCPU、CUDA、HIP、Vulkan等に対応し、複数の整数量子化とCPU・GPU混合推論を提供する。[llama.cpp公式README](https://github.com/ggml-org/llama.cpp/blob/master/README.md) と [バックエンド対応表](https://github.com/ggml-org/llama.cpp/wiki/Feature-matrix) を参照。本体は [MIT License](https://github.com/ggml-org/llama.cpp/blob/master/LICENSE) である。

- 長所: アプリがバージョンと起動を所有し、利用者へ別アプリを要求しない構成を作れる。
- 短所: Windowsネイティブバイナリ、GPU別バックエンド、モデル取得・検証、子プロセス監視、終了、タイムアウト、ライセンス表示を製品側で所有する必要がある。
- きゃすメイトへの実装難易度: 高

OllamaはWindows上で動作し、インストール後は既定で `http://localhost:11434` にローカルAPIを提供する。[Ollama Windows公式文書](https://docs.ollama.com/windows) を参照。ローカルAPIは認証不要で、クラウドモデル等は別途認証が必要である。[Ollama認証仕様](https://docs.ollama.com/api/authentication) を参照。

公式文書はWindows版バイナリ用に少なくとも4 GB、さらにモデル保存領域が必要としている。利用者にOllamaの導入・起動・モデル取得を要求するなら統合は比較的容易だが、アプリ単体で完結しなくなる。

- 長所: HTTP APIで試作しやすい。
- 短所: 別ソフトの導入状態、更新、起動状態に依存する。
- きゃすメイトへの実装難易度: 中。ただし外部依存を受け入れる場合に限る。

### モデル容量とライセンスの例

Qwen3.5 0.8Bの公式モデルはApache 2.0で、元の重み一式は約1.77 GBである。[Qwen公式モデルカードとファイル一覧](https://huggingface.co/Qwen/Qwen3.5-0.8B) と [LICENSE](https://huggingface.co/Qwen/Qwen3.5-0.8B/blob/main/LICENSE) を参照。Ollamaの量子化済み `qwen3.5:0.8b` は約1.0 GB、2Bは約2.7 GB、4Bは約3.4 GBである。[Ollama公式タグ一覧](https://ollama.com/library/qwen3.5/tags) を参照。

これは容量の目安であり、日本語の自然さ、生成時間、禁止事項の遵守率を保証するものではない。採用時は、候補モデルごとに対象PCで次を比較する必要がある。

- 初回読込時間、短文生成時間、ピークRAM・VRAM、CPU・GPU使用率
- OBS、VOICEVOX、配信者音声認識と同時実行したときの影響
- 日本語の自然さ、同文率、話題逸脱率、禁止語・文字数の遵守率
- モデルと推論エンジンそれぞれの再配布条件

### きゃすメイトへの適合性

現行アプリはElectron、VOICEVOX、OBSに加え、CPU 4スレッド固定の配信者音声認識ワーカーを同時に使いうる。[配信者音声認識仕様](../features/streamer-speech-recognition.md) を参照。ローカルLLMを既定で動かすと、配信中のPC資源を競合させる可能性がある。

任意機能にする場合は、自由生成ではなく、内蔵話題カードから選んだ安全な一文の短い言い換えだけに限定する。生成には厳しいタイムアウトを設け、次を満たさない出力は破棄して元の文へ戻す。

- 一文かつ上限文字数以内
- URL、制御文字、禁止語を含まない
- 指定した話題カテゴリから逸脱しない
- 直近出力と重複しない

ネイティブ推論を同梱する場合は、既存の音声認識と同様に独立ワーカーへ分離し、その障害でコメント取得、表示、読み上げを停止させない設計が適合する。[ADR 0006](../adr/0006-isolate-speech-recognition-in-dotnet-worker.md) を参照。

## 5. 無料の情報源から話題を取得する

外部情報源は文章生成器ではなく、話題の「素材」である。見出しや本文をそのまま投稿するのではなく、許可したデータ項目だけを短い自作テンプレートへ差し込む方が安全である。

### 気象庁

気象庁は公開XMLのPULL型提供を行い、ユーザー登録不要としている。一方、メンテナンス等による停止・遅延があり、迅速・確実な配信は保証されない。[気象データ高度利用ポータル](https://www.data.jma.go.jp/developer/) を参照。

公開コンテンツの二次利用は原則として商用利用も可能だが、気象庁を出典として明記し、編集・加工時はその旨と編集責任も示す必要がある。独自予報や警報の扱いには法令上の制限がある。[気象庁「ご利用上の留意事項」](https://www.data.jma.go.jp/developer/ryuui.pdf) を参照。

- 継続料金: なし
- 実装難易度: 中。地域設定、取得、XML/CSV解析、キャッシュ、出典、障害時フォールバックが必要
- PC負荷: 低
- 話題の自然さ: 「今日は暑いね」「雨の日は何をして過ごす？」など日常話題にしやすい
- 注意: 警報、地震、災害情報は軽い雑談へ加工せず、この機能の入力から除外する

補助情報源としては有力だが、これだけを必須にするとオフラインで動かず、地域未設定時も使いにくい。

### Wikimedia / Wikipedia

MediaWiki REST APIはWikipedia等のコンテンツへJSONまたはHTMLでアクセスできる。[MediaWiki REST API公式文書](https://www.mediawiki.org/wiki/API:REST_API) を参照。APIにはレート制限があり、2026年の制限値は実験・変更対象で、HTTP 429/503と `Retry-After` への対応が必要である。[Wikimedia APIレート制限](https://www.mediawiki.org/wiki/Wikimedia_APIs/Rate_limits) を参照。

日替わり話題に見えるWikifeeds APIは、2026年7月から段階的廃止予定で、代替経路も未定である。[Wikifeeds API公式文書](https://www.mediawiki.org/wiki/Wikifeeds_API) を参照。したがって新機能の基盤には採用しない。

通常の検索やランダム記事取得を使う場合も、記事本文のライセンス、出典表示、センシティブ記事、配信との無関係さを処理する必要がある。本文をそのまま再投稿せず、許可カテゴリの短い題名を話題候補にする程度でも、外部依存としてキャッシュと内蔵話題へのフォールバックが必要である。

### RSS / Atom

AtomはWebコンテンツとメタデータの配信形式を定める正式仕様である。[RFC 4287](https://www.rfc-editor.org/rfc/rfc4287.html) を参照。RSS/Atomはデータ形式であり、配信される見出しや本文の転載許諾ではない。各提供元の利用規約、著作権、取得頻度、商用利用条件を個別に確認する必要がある。

任意URLのRSSを製品既定の情報源にするより、利用条件と安定性を確認した少数の公式ソースだけをサービス別アダプターとして採用する方が、外部障害を分離する現行方針に合う。

### Open-Meteo

Open-Meteoの無料APIは非商用利用向けで、広告や購読を含む商用製品への統合は商用利用例として有料プランの対象になる。[Open-Meteo公式利用規約](https://open-meteo.com/en/terms) と [公式料金表](https://open-meteo.com/en/pricing) を参照。

将来の配布・収益化条件に左右されるため、本調査の「完全無料で運用できる情報源」には分類しない。

## 6. その他の低コスト方式

### ローカルのカレンダー・時刻・季節

料金、通信、モデルを必要とせず、「もう夜だけど、みんなは夜更かし派？」「週末は何をして過ごすことが多い？」のような文を選べる。自作話題カードと最も相性がよい。

祝日名など更新が必要な事実を使わず、曜日、月、時間帯だけを使えば、追加データ更新も不要である。

### 配信者が話題カードを追加する

配信者自身がゲーム名、趣味、配信固有の質問、避けたいカテゴリを登録すれば、低負荷のまま関連性を大きく上げられる。利用者作成カードが空または無効でも、内蔵カードへ戻せる。

### 直近コメントからのローカル選択

自由文を再生成するのではなく、許可済みキーワード辞書との一致で内蔵話題カテゴリを選ぶ方式なら、低負荷かつ外部送信なしで関連性を上げられる。

個人名、投稿者名、URL、金銭、健康、攻撃的表現を候補にせず、コメント本文を学習データとして永続化しない。抽出語をそのまま出力するのではなく、安全なカテゴリ選択だけに使う。

## 推奨アーキテクチャ

### 初期版: 完全オフラインのコア

1. 内蔵話題カードを、カテゴリ、利用可能な時刻・季節、複数の完成文、重複グループ、既定の有効状態とともに持つ。
2. 配信者が配信カテゴリ、使用する話題カテゴリ、追加カードを設定できる。
3. X分間、対象となる人間の新着コメントがない場合だけ候補を選ぶ。
4. 同一文、同一カード、同一カテゴリ、同一導入句のクールダウンを別々に管理する。
5. 投稿前に文字数、URL、禁止語、重複を検査する。
6. 生成物は「きゃすメイト」など自動生成と分かる専用投稿者として表示し、視聴者の実在コメントに偽装しない。
7. 生成履歴は配信セッション中だけ保持し、アプリ終了時に破棄する。

### 任意拡張A: 許可した情報源

1. 情報源ごとの独立アダプターで低頻度取得する。
2. 取得済みキャッシュだけを話題候補に使う。
3. コメント本文、投稿者名、接続先、認識結果を外部情報源へ送らない。
4. 出典と加工表示が必要な情報は、表示面で条件を満たせない限り使わない。
5. タイムアウト、HTTP 429/503、解析失敗、規約変更時は、その情報源だけを停止して内蔵話題へ戻る。

### 任意拡張B: ローカルLLMによる言い換え

1. 既定はオフとし、モデル取得と必要容量を配信者へ明示する。
2. 承認済みの内蔵話題一文と口調指定だけを入力する。
3. 短いタイムアウトと一回の生成上限を設ける。
4. 出力検査に失敗したら再生成を繰り返さず、元の話題文を使う。
5. 独立ワーカーとして実行し、CPU・GPU負荷と他機能への影響を実機評価する。

## 外部コメント投稿との境界

本調査の推奨は、まずアプリ内部で自動生成した共通コメント相当の表示・読み上げを行う前提である。YouTube Live、Twitch、したらばへ実際に書き込む機能は、話題生成とは別の仕様と設計判断にする必要がある。

- YouTube Liveへのメッセージ追加はOAuth 2.0の認可スコープを必要とし、投稿過多のレート制限もある。[YouTube Live `liveChatMessages.insert`](https://developers.google.com/youtube/v3/live/docs/liveChatMessages/insert) を参照。
- Twitchの送信APIはBearerトークンとClient IDを使い、botの送信者IDを指定する。[Twitch「Sending and Receiving Chat Messages」](https://dev.twitch.tv/docs/chat/send-receive-messages/) を参照。
- 現行v0.4.0は公式API認証と一般コメント投稿を対象外とし、したらばへの書き込みも次スレッド作成に限定している。[OUT_OF_SCOPE.md](../../OUT_OF_SCOPE.md) と [ADR 0004](../adr/0004-limit-shitaraba-write-to-next-thread.md) を参照。

したがって本機能を正式採用する際は、最初に「内部の自動コメント」か「外部サービスへの実投稿」かを決める。後者はログイン、資格情報、送信失敗、連投制御、サービス規約、視聴者へのbot表示を含む別機能として設計する。

## 最終提案

初期版は、**自作話題カード＋型付きテンプレート＋ローカル時刻・季節・配信カテゴリ＋クールダウン**で実装する。外部情報源とローカルLLMは含めず、データと選択ロジックを後からプロバイダー追加できる境界にする。

この方式は次の点で、きゃすメイトに最も適している。

- API利用料、アカウント、クラウド、ネット接続が不要である。
- OBS、VOICEVOX、配信者音声認識とPC資源をほぼ競合しない。
- 配信へ出る全文を出荷前に確認でき、事故を抑えやすい。
- 現行のローカル優先、データ非送信、障害分離の方針と一致する。
