# 外配信の追加機能候補調査

調査日: 2026-10-14。対象は、きゃすメイトのAndroid外配信で便利さや印象に残る体験を増やす機能。現行仕様と競合・技術の一次情報を照合した。以下は**未採用の調査・提案**であり、正式仕様ではない。優先順位と開発負担は調査担当者の評価で、利用者需要や開発日数を実測したものではない。

## 推奨する方向

まず検討するなら、**実用性はOBS本番確認、見どころ作りは「今の場面を保存」、独自性は視聴者参加の街歩き企画**が有望と判断する。手書き、コメント集約、複数スマホ、音声認識を個別に拡張するだけでなく、「投票で企画を進める → 手書きで対象を示す → 見どころを保存する」という一連の使い方へつなげると、きゃすメイトの特徴が出る。

競合の採用例は機能が実在する根拠として扱う。人気、利用頻度、利用者が購入する意思、きゃすメイトでの性能までは証明しない。

## 追加候補の比較

負担の「中」は既存連携を拡張する設計・テスト、「大」は映像処理や新しい通信・障害処理を含む見込み。「小〜中」も実装済みという意味ではない。便利さと目立ちやすさは相対評価。

| 候補 | 外配信での使い方 | 便利さ | 目立ちやすさ | 初版の負担 |
| --- | --- | --- | --- | --- |
| 1. OBS本番確認 | スマホでOBS合成結果の小画像、現在シーン、マイク入力・ミュート状態を見る | 高 | 中 | 中 |
| 2. 「今の場面を保存」 | 面白い瞬間の後に押し、PCへ直前30秒を残す。再生は次段階 | 高 | 高 | 中 |
| 3. 視聴者参加の街歩き企画 | 「海か商店街か」を投票、探索ミッション、達成カードを表示 | 中 | 高 | 中 |
| 4. 部分マスク・顔ぼかし | 指で住所等を隠す。次段階で顔に自動追従 | 高 | 高 | 手動は中、自動は大 |
| 5. 番組プリセット | 「景色」「顔＋景色」「料理アップ」「休憩」をスマホで切替 | 高 | 中〜高 | 中 |

| 9. 回線断の自動待機シーン | 復旧中の案内へ切替、映像が戻ったら通常画面へ復帰 | 高 | 中 | 中〜大 |
| 10. 翻訳字幕・翻訳コメント | 日本語の確定字幕を英語にし、外国語コメントを日本語で聞く | 中〜高 | 高 | 中〜大 |

各行は独自提案で、上表の実在機能をそのまま製品仕様にするものではない。

### 1. OBS本番確認

送信側プレビューと、OBSのシーンで合成された結果を並べて確認する。初版は「確認」ボタンで低解像度の静止画像を取得し、取得時刻、現在シーン、入力音量・ミュートを表示する案。常時動画・音声の返送は通信量、遅延、音の回り込みを伴うため別段階にする。

画像取得の技術的根拠は[OBSのGetSourceScreenshot](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md#getsourcescreenshot)。既存の[ObsVisual](../../src/main/obs/obs-visual.ts)はAIリスナー用に指定ソースの画像を取得するが、今回のシーン全体確認やスマホへの返送は新しい機能になる。**OBSで描画されていること、入力に音量があること、視聴者へ届いていることは別**と表示する。

### 2. 「今の場面を保存」

スマホで押すとOBSのリプレイバッファを保存し、完了を返す。30秒は初版の提案値であり、保存時間を設定・有効化する準備が必要。最初は保存だけで成立し、サムネイル一覧や配信中の再生を後から加えられる。[保存API](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md#savereplaybuffer)、[保存完了イベント](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md#replaybuffersaved)

面白い動物、食べ物を見せた瞬間、ハプニングなどを配信後の短編素材にできる、という評価。コメントから「保存リクエスト」を出す案もあるが、保存の連打を防ぐ上限を定める。保存要求の受付とファイル保存完了を区別し、バッファ未開始・容量不足・結果不明を扱う。

保存できるのはOBSに届いた映像。回線断中の現場映像を残すには、別の**スマホ独立録画**が必要になる。後者は有用な追加候補だが、端末の発熱・容量・送信との同時継続を独立して検証する。

### 3. 視聴者参加の街歩き企画

初版は既存の通常コメントから、配信者が開始した選択肢の数字を締切まで集計する。「次に見たいのは1:海、2:商店街」「赤い看板を見つけよう」などの企画カードをOBSへ表示し、結果を読み上げる。配信者が採用した結果を手書きや達成カードへつなぐ。コメント投票・操作の発想には[Moblin](https://github.com/eerimoq/moblin/blob/main/README.md)と[チャット操作ガイド](https://github.com/eerimoq/moblin/blob/main/docs/chat-bot-help.md)の先例がある。

きゃすメイトは複数サービスのコメントを集約するため、共通の投票体験を作れる可能性がある。投票締切、同票、連投、匿名掲示板での票の単位、複数サービスで同一人物を識別できない場合を決める。視聴者に任意のOBS操作権限を与える必要はなく、配信者が用意した候補への参加から始める。

Twitch公式投票やChannel Points連携は別段階。公式投票の作成はOAuth権限が必要で、通常コメントだけの集計とは異なる。[Create Poll](https://dev.twitch.tv/docs/api/reference/#create-poll)の契約と[現在の利用条件](https://help.twitch.tv/s/article/how-to-use-polls?language=en_US)を採用時に確認する。通常コメントの集計自体も新規採用が必要。

### 4. 部分マスク・顔ぼかし

初版は手書きの操作感で画面の一部を塗りつぶす案。カメラを固定し、対象が同じ画面位置にある場面に向く。カメラや対象が動くと隠す範囲がずれる。動く通行人には自動顔検出で追従する段階が必要で、固定領域と自動追従を同じ保護性能として扱わない。

Androidで顔の矩形と追跡IDを得る根拠は[ML Kitの入力条件・追跡設定](https://developers.google.com/ml-kit/vision/face-detection/android)。暗所、小さい顔、横顔、速い動きで検出漏れが起こり得るため完全な遮蔽とは位置付けない。スマホでSRTエンコード前に処理する案と、PCのOBS側で処理する案を比較し、どの地点まで原画像が送られるか明確にする。

## 他候補を採用するときの主な条件

| 候補 | 最初に区切る範囲・具体的な制約 |
| --- | --- |
| 番組プリセット | PCで用意したシーンを限定して切替。複数端末の遅延差、使うマイク、操作失敗後の表示を決める。PRISMの同一Wi-Fi事例からWAN対応済みとは判断しない |
| 屋外音声モード | PCのOBSフィルターで比較試聴する段階から。現行のゲイン・ミュートとは別。強風による音の破損や強い騒音が完全に消えるとは約束しない。フィルター編集を自動化する場合は追加のOBS操作になる |
| 手元を見ない操作 | 初版は端末内のミュート・映像隠しに絞る。音量操作との競合、ロック中、誤入力を実機確認。保存・OBS操作・音声コマンドは別途追加する |
| 電池・熱・通信量 | まず計測・警告・明示操作の案内。電池残時間は推定、通信量はアプリが測る範囲を示す。発熱による解像度等の自動変更は現行対象外であり別設計 |
| 自動待機シーン | 送信量だけで映像復帰を断定せず、PC受信・OBS状態の確認条件を決める。短い不調による往復、手動休憩中の自動復帰を防ぐ。自宅PC側の配信停止はこれだけで救済できない |
| 翻訳字幕 | 既存PCの確定文を起点に日本語→英語から試す。誤認識、固有名詞、翻訳遅延、長文の表示を評価。ML KitはWindows向けSDKではないため、PCの翻訳エンジン選定は別調査。[翻訳の限界](https://developers.google.com/ml-kit/language/translation#limitations) |
| 旅のHUD | 初版は地域名・企画・到着チェックの手入力でも成立。位置公開を採用する場合は粗い地域表示・公開遅延・非公開地点を定め、現在地や自宅の軌跡を不用意に公開しない |

## 採用・検証へのつなぎ方

着手候補を3つに絞るなら、次の問いを小さく検証する。

1. **OBS本番確認:** 静止画像とマイク状態だけで、現場の「映っている・音が出ている」の不安を減らせるか。
2. **今の場面を保存:** 配信者が操作を覚えなくても使え、配信後に使える30秒素材が残るか。
3. **街歩き企画:** 数字投票と達成カードだけで、コメント数の少ない配信でも企画を進められるか。

見栄えを優先する場合は4の顔ぼかし、12の追従注釈を別の試作候補にする。便利さを優先する場合は5の番組プリセット、6の屋外音声、8の配信予算を続ける。

OBSシーン切替・録画・映像返し、発熱による自動品質変更、複数回線などは[今回の対象外](../../OUT_OF_SCOPE.md)に記載があり、OBS確認支援などは[将来候補](../../FUTURE_IDEAS.md)にも記録されている。本調査の候補数には既存の未採用案の具体化も含む。実装する際は、採用する範囲だけ機能仕様・必要なADR・SPEC.md・対象外一覧の整合を更新する。

新しい外部接続はサービス単位で分離する。画像・位置・コメントを外部へ送る案では、送り先、用途、保存、料金をその機能の仕様で定める。OBS操作は既存のPC経由の用途別認証を拡張する方向で検討し、OBS WebSocket本体や一般管理APIを公開しない。[開発ルール](../../AGENTS.md)、[直接接続の境界](../features/smartphone-direct-connection.md)

今回の成果は調査文書のみ。製品コード・正式仕様・採用状態の変更、実配信の試験、配布物の生成は行っていない。文書内のローカル参照先と差分を確認し、コード変更向けのlint・型チェック・全体テスト・ビルドは実施していない。
