# 開発運用の改善案

作成日: 2026-09-17

状態: 2026-09-17に正式反映。正式な運用は[AGENTS.md](../../AGENTS.md)と[開発の運用手順](../development-workflow.md)、反映時の結果は[検証記録](../validation/development-workflow-2026-09-17.md)を参照する。以下は承認時の計画を残した履歴資料であり、現行の指示として重ねて適用しない。[事前レビュー](./agent-workflow-improvement-review-2026-09-17.md)で自己レビュー後に2名の最終レビューを実施した。

## 目的と維持するもの

仕様の見落としを増やさず、不要な全文読み、探索、検証のやり直しを減らす。トークン削減率や文書の短さ自体を合格条件にはしない。

分割仕様方式、正式仕様の単一所有、仕様更新を先に行う順序、正式用語、採用済みADR、障害分離、プライバシー、明示依頼時だけの配布物生成を維持する。全体検証とレビューの品質を維持する。

根拠は[現行AGENTS.md](../../AGENTS.md)、[SPEC.md](../../SPEC.md)、[管理画面仕様](../features/management-screen.md)、[ローカルアプリケーション仕様](../features/local-application.md)、[直近の検証記録](../validation/mobile-speech-ui-2026-09-17.md)。現状は管理画面仕様約27,400字、うち個別編集画面の節は約10,000字。全630テストは直近の直列実行で約241秒。これらは文字数と実行時間であり、消費トークンの測定値ではない。

## 1. 文書の配置と変更範囲

| 文書 | 反映する内容 | 反映しない内容 |
| --- | --- | --- |

| CONTEXT.md | 現行の用語定義を維持し、必要な節を参照 | 別の用語集への複製 |
| docs/features/management-screen.md | 共通レイアウト、ホーム、分類・移動、通知、PC状態、共通受け入れ条件 | 個別編集画面の詳細の継続所有 |
| 対応する機能仕様7件 | 各編集画面の節を移動し、共通仕様へリンク | 共通ルールのコピー、移動に伴う機能変更 |

運用手順の詳細はdocs/development-workflow.mdの一箇所で管理する。AGENTS.mdには省略できない原則と参照条件を残す。新しい運用文書は目安として150行以内に収め、文字数のために必須条件を削らない。

SPEC.mdの概要・目的、対象バージョン、機能一覧と説明、機能仕様へのリンク、OUT_OF_SCOPE.mdとFUTURE_IDEAS.mdへのリンクは維持する。運用文書の「文書の役割」にこの役割を簡潔に記載する。機能仕様は具体的な挙動・条件・例外・他機能との関係を所有する。

## 2. AGENTS.mdの置換案

以下は正式反映時の候補本文。リンクはリポジトリルートのAGENTS.mdから解決する。現段階では新規の運用文書はまだ存在しない。

```markdown
# きゃすメイトの開発ルール

## 正式仕様

- SPEC.mdを全体仕様と機能索引、docs/features/を機能別の正式仕様とする。原則1主要機能1仕様とし、正式仕様は所有文書だけに記載する。他の仕様はコピーせず参照する。
- SPEC.mdから参照される機能だけを実装する。OUT_OF_SCOPE.mdは今回の対象外、FUTURE_IDEAS.mdは未採用案とする。採用時は機能仕様とSPEC.mdを更新してから実装する。
- 仕様の矛盾や重要な未定義挙動は、確認または所有文書の更新を先に行う。正式用語はCONTEXT.md、重要な設計判断は関連ADRに従い、理由なく覆さない。

## 読む範囲

- 作業開始時にSPEC.mdで対象を確認し、対象仕様の所有範囲・見出し・他機能との関係を把握する。変更に関係する挙動、例外、エラー、受け入れ条件と関連用語・ADRを読む。
- 変更前に[運用手順の読み取り判断表](docs/development-workflow.md#読み取り判断表)で該当する全ての行を確認する。影響範囲が不明、依存先との矛盾、共有処理への変更がある場合は調査範囲を広げる。
- 一度読んだ内容が現在の作業文脈で確認でき、ファイルが変わっていなければ全文再読を省く。要約だけでは判断できない場合や中断・別作業による変更がある場合は必要な原文を確認する。

## 実装と検証

- 管理画面の変更では[設定編集画面の共通レイアウト](docs/features/management-screen.md#設定編集画面の共通レイアウト)を確認する。通知・操作結果・処理中表示の変更では[通知で操作位置を動かさない共通ルール](docs/features/management-screen.md#通知で操作位置を動かさない共通ルール)と[共通トースト](docs/features/management-screen.md#共通トースト)を実装・レビュー・検証の必須対象とする。
- 変更する挙動をテストで検証する。必要な回帰テストを追加・更新し、作業中は関連テスト、実装完了前はlint・型チェック・全体テスト・pnpm buildを実行する。変更種別、再実行条件、実機確認は[検証手順](docs/development-workflow.md#検証手順)に従う。失敗や未実施を成功扱いしない。
- 共通部品・共有型・保存・API・公開範囲などの変更は、直接の利用箇所だけでなく影響する利用側を確認する。レビュー範囲は[レビュー判断](docs/development-workflow.md#レビュー判断)に従う。
- 外部接続はサービス別に分離し、一つの障害で他サービスやアプリ全体を停止させない。
- コメント本文・接続先・設定値を、本機能に不要なテレメトリー・分析・クラッシュレポート等へ送信しない。コメント取得に必要な接続先情報は対象サービスに必要最小限だけ送信する。
- 配布物は利用者の明示的な依頼がある場合だけ生成する。インストーラーはpnpm package:win、展開版EXEはpnpm exec electron-builder --win dir。通常の完了検証はpnpm buildまでとする。
```

上記は現行ルールの無条件緩和ではない。「読む範囲」は次の判断表と一体で反映する。

### 現行ルールの保存先

| 現行AGENTS.mdの規則 | 置換後の保存先 |
| --- | --- |
| 分割仕様、主要機能単位、単一所有、コピーしない | 候補本文「正式仕様」第1項 |
| SPEC.mdに書く5項目、機能仕様の具体性 | 運用文書「文書の役割」。本案1節に内容を指定 |

| 通知と操作位置の共通ルール | 候補本文「実装と検証」第1項。既存の直接リンクを維持 |

削除するのは重複説明と仮のファイル名の例示であり、上記以外の規則を暗黙に廃止しない。

見出しやキーワード検索は読む場所を探す手段とし、検索に一致した一文だけで仕様を判断しない。対象段落の条件と例外を含む節単位で読む。対象範囲が不明なら対象仕様の全文へ広げる。

## 5. 調査入口の記載案

初回はmanagement-screen.md、local-application.md、mobile-speech.mdの3文書で試行し、他の機能は次に変更する際に必要なら追加する。全機能の依存一覧は作らない。

各文書に「調査入口（仕様ではない）」を置き、主な実装入口、代表的なテスト、関連共通仕様へのリンクを少数だけ記載する。行番号、内部関数、実行結果、実装済みかどうかの状態は載せない。

mobile-speech.mdに置く例（リンクは正式反映時に同ファイルからの相対パスにする）:

| 種類 | 入口 |
| --- | --- |
| 主な実装 | src/renderer/components/MobileSpeechPanel.tsx、src/main/speech/mobile-speech-controller.ts |
| 代表的なテスト | tests/mobile-speech-panel.test.tsx、tests/mobile-speech-controller.test.ts |
| 関連する共通契約 | 管理画面の共通レイアウト・通知、ローカルアプリケーションの設定保存 |

「入口は影響範囲の全件一覧ではない。変更前に実際の参照元と関連テストを検索する」と明記する。リンク先を移動・削除した作業で入口も更新する。コードの事実と食い違えばコードを調べて入口を修正し、入口を根拠に影響箇所を除外しない。

## 6. 検証手順

### 作業中と完了時

1. 作業開始時に変更種別と影響範囲を判断する。全体検証が直前に済んでいても、その後の変更や環境の違いを確認する。
2. 実装中は対象の挙動を確認するテストを追加・更新し、関連テストを実行する。既存テストで十分な場合は実装をなぞるだけの重複テストを増やさない。
3. 実装をまとめた後にpnpm lint、pnpm typecheck、pnpm test、pnpm buildを実行する。負荷の高い全体テストとビルドは同時に実行しない。
4. 成功した対象からコード・設定・依存関係・実行環境が変われば必要な検証を再実行する。共有処理・API・保存・依存関係・検証設定の変更や影響不明の場合は全体検証へ戻す。実行回数の上限は設けない。
5. 機能仕様にあるUI・Electron・Android・実サービスの確認は、自動テスト成功で代替しない。実施できなければ未検証の範囲を報告する。

### 変更種別

| 種別 | 最終確認 |
| --- | --- |
| 製品コード、CSS、テストコード、依存・ビルド・検証設定 | lint、型チェック、全体テスト、ビルド。対象仕様に応じた画面・実機確認 |
| 純粋な文書の移動・リンク・表記整理 | 差分、リンク先とアンカー、所有範囲、移動前後の条件・例外の保存を確認。製品コードが不変なら全ビルドを要求しない |
| 正式仕様の意味変更 | 対応する実装・既存テストとの整合を確認。コード変更を伴えば実装の全体検証を適用。文書のみで完了とするなら、その理由と未実装の有無を明示 |
| AGENTS.md等の運用変更 | 旧ルールからの対応付け、参照先、代表的な作業例で判断が一意になるか確認。実行スクリプトも変更する場合はコード変更として検証 |

拡張子だけで文書変更と分類しない。生成・配布・テスト・アプリ実行が読む文書やテンプレートは、その利用側の検証も必要になる。仕様の意味変更で実装が追いついていなければ「仕様更新済み・実装未完了」と区別し、実装を含む依頼の完了にはしない。

運用文書の検証規則とREADME.mdの開発手順、AGENTS.mdを同時に整合させる。機能仕様が求める実機確認・受け入れ条件は、この一般表で免除できない。

### 失敗と再実行

失敗したコマンド、対象、要点を記録し、原因に対応する修正・条件変更をして再実行する。同条件で成功するまで繰り返さない。並列数を下げた成功だけでタイムアウト原因を確定しない。

現状のlint失敗は別途調査する。候補は異常なエントリーの原因確認、またはルート設定・スクリプト・見本も含めたlint対象の明示化。src/testsだけの実行を全体lint成功と同一視しない。不正なパスの無断削除や、検証を通すためだけの除外をしない。

全体テストの並列数は再現条件と所要時間を確認して選ぶ。特定の並列数を恒久的な正解と決めない。検証結果には対象差分、コマンド、成否、制約を短く残す。ログ全文は必要時に参照する。

## 7. レビュー判断

全ての変更で、要求との一致、影響範囲、例外・失敗時、検証結果を担当者が確認する。ファイル数や行数だけで低リスクと判断しない。

共有処理、設定移行、公開・認証、外部書込み、配信制御、複数機能にまたがる変更、仕様の曖昧さを解消した変更では、実装後に「仕様との一致」と「故障時・影響範囲」の2観点を分けた追加レビューを必須とする。UI変更でも状態管理・保存・非同期表示を変えれば該当する。運用ルールの変更も必須条件の脱落を確認するため、この区分で扱う。

追加レビューを必須とすることと、別エージェントを必ず起動することは区別する。別担当による独立レビューを利用でき、かつその利用が許可される場合は優先する。利用しない場合は担当者が編集工程を終えてから2観点を別々に確認し、自己レビューであることと制約を記録する。重大な未解決指摘は解消するまで完了扱いにしない。適用する指示・スキルが独立レビューを必須とする場合、この代替は使用しない。

既存スキルが複数観点や別エージェントによるレビューを要求する場合は省略しない。利用可能な作業手順の選択は適用条件とリスクに基づき、必須レビューを避けるために選び直さない。

減らす対象は、同じ原文の無意味な再取得、大量の成功ログ、短間隔での状態確認、同じ観点の二重確認。追加レビューで判明した不具合の価値は維持する。

## 8. 反映の順序と合格条件

1. 本案をレビューし、指摘を反映する。レビュー記録を別ファイルへ保存する。
2. 運用文書を作成し、AGENTS.mdとREADME.mdの参照を同時に更新する。新旧ルールの対応を確認し、参照だけ先に作らない。
3. 個別画面仕様を7節移動する。移動元→移動先の一覧を使い、全条件・例外が保存され、共通仕様が複製されず、既存リンクが解決することを確認する。
4. 調査入口を3文書で試行する。リンクが存在し、対象機能の実装とテストへ到達することを確認する。
5. lint・テストの安定化は文書整理と差分を分けて実施し、既存の検証範囲を狭めていないことを確認する。製品挙動の変更はこの計画に含めない。
6. 続く3件程度の開発で効果を確認する。読み取り範囲、全体検証の再実行理由、仕様の見落としによる手戻り、追加レビューの発見を既存の検証記録に数行だけ残す。報告のために新しい詳細ログ基盤は作らない。

手順2〜4は運用文書・仕様文書の整理としてまとめられる。手順5は個別の原因調査・コード検証を伴う別の変更単位とし、安定化が未完了でも文書整理を全体lint成功と報告しない。運用文書を作る際の見出しは「文書の役割」「読み取り判断表」「検証手順」「レビュー判断」「運用の評価」とし、AGENTS.mdからのリンク先を一致させる。

評価では変更の難しさ・影響範囲の違いを考慮し、トークン実測がない場合は文字数等を代替指標として明示する。見落としが増えた場合は該当する読み取り条件を強める。入口の保守負担が効果を上回る場合は試行を縮小する。正式仕様を失わせる巻き戻しは行わない。

初回反映の完了条件: 現行の必須ルールが保存され、新旧リンクが解決し、仕様所有者が一意で、検証・レビューの省略条件が曖昧でないこと。効率改善の効果は初回反映だけでは実証済みとしない。
